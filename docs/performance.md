# 性能基线与首轮优化

## 可重复测量

运行 `npm run benchmark -- /tmp/ai-player-performance.json`。脚本使用固定的 200 / 2,000 节合成课程、Vue 响应式对象、10 次预热及 100 次采样，报告中位数与 P95。数据不来自用户课程库。保存测试替换数据库边界，只统计实际业务代码发起的写入次数。

本轮基线来自提交 `0db31fe` 的原有计算和保存实现；原始结果见 [优化前](performance/before.json) 和 [优化后](performance/after.json)。环境为 macOS arm64、Node 24.19.0。

| 项目                             | 优化前    | 优化后    |
| -------------------------------- | --------- | --------- |
| 2,000 节课程读取今日预算，中位数 | 6.107 ms  | 0.013 ms  |
| 同上 P95                         | 6.358 ms  | 0.017 ms  |
| 切换 50 次视图时保存实践记录     | 50 次     | 1 次      |
| 同一场景保存导学 / 日快照        | 50 / 1 次 | 50 / 1 次 |

全量排课与快照的算法未在本轮提速，测量仍约 6–7 ms，最后一次复测略慢；需在相同机器、相近负载下持续对比。这些是局部 CPU 耗时和写入次数，不能解读为整机启动速度、真实磁盘耗时或帧率提升。

## 已落地的改动

- 预算、实践任务计算与完整视频排课分开；普通预算读取不遍历课程、元数据和观看进度。
- 显式监听待学片段的完成状态及实际时长，保持进度自动同步，不依赖预算重算的附带作用。
- 导学、实践与快照分别去重，失败仍允许相同内容重试，过期失败不能清空更新版本的保存状态。
- 日快照使用独立的计算缓存，切换目录视图不会反复生成全量排期。
- 桌宠相同状态采用两秒心跳；变化即时发送，显式同步立即回应。

## 实际运行耗时

标准 Performance 面板中可查看以下本地记录，名称不包含课程、路径或笔记内容：

- `ai-player:webview-ready`：WebView 导航开始到应用挂载，包含前端模块加载；不是原生进程冷启动耗时。
- `ai-player:home-load`：首页读取与日快照处理完成。
- `ai-player:course-open`：课程恢复完成。
- `ai-player:video-ready`：请求媒体源到 `loadeddata`，表示首帧数据可用，并非屏幕呈现的测量。
- `ai-player:note-ready`：按需加载编辑器到笔记就绪。

取消或失败操作不计入成功样本。每个标签仅保留最新 Performance 记录，应用内统计最多保留 200 个样本；不向外发送。后续采样应记录首次 / 再次打开、课程数量、字幕长度、窗口尺寸与系统负载。

## 持续测量

编辑器已经按需加载，当前产物仍约 1.06 MB；本轮优化的是输入转换与加载顺序，后续插件调整需以实际初始化耗时为依据。大目录和长字幕的按需渲染还需持续覆盖不同窗口尺寸与文本行高。不要仅通过拆文件或减少可见功能宣称性能改善。

## 第二轮：交互与完整排课

六项后续优化均已实现：

- 超过 100 节的课程列表、超过 150 句的字幕采用可变行高的按需渲染。目录先平铺已展开分支，再交给列表；搜索和当前项定位使用行索引，并只滚动所属容器。
- 笔记输入立即标记未保存，但把 Markdown 转换合并到保存或显式读取时执行。保存、切课和销毁前先取得最新文档，保存中继续输入仍使用同一写入队列。
- 知识点缓存按 24 项、约 4 MB 文本量清理旧结果。当前使用、生成中、保存失败的结果受保护，可暂时超出限制；释放后继续清理。
- 自动知识点准备等待视频首帧，再延后 800 ms；快速切课取消旧自动任务，显式使用的任务得到保护。未配置 AI 且没有字幕时不会自动启动转写。
- 完整排课按路径索引已完成片段和未完成片段，按需计算补学状态，并在排课与剩余时长计算间共用时长估算，保持原有结果。
- 设置页新增“关于与诊断”，显示版本、提交号、构建时间和本地耗时统计，可导出 JSON 报告。只导出构建信息、窗口尺寸及聚合耗时。

| 压力场景                                       | 优化前     | 优化后   |
| ---------------------------------------------- | ---------- | -------- |
| 2,000 节短课、800 个当日已完成片段，重排中位数 | 132.298 ms | 3.841 ms |
| 同上 P95                                       | 133.644 ms | 4.219 ms |
| 连续 100 次输入的 Markdown 转换次数            | 100 次     | 1 次     |

排课比较在同一进程中对原实现和当前实现各预热后采样 20 次，并先断言两者输出完全一致。输入转换次数由实际笔记会话逻辑测量，不能代替真实编辑器输入延迟。原始数据见 [排课索引比较](performance/day-index-comparison.json) 和 [第二轮基准](performance/round2.json)。

## 第三轮：增量读取、编辑器加载与性能门槛

- 首页和学习管理共享读取缓存。首次读取完整课程与学习材料，后续按课程失效；保存笔记只重读对应课程的材料，进度变化只重读对应课程的计划数据。并发请求合并，读取期间的新修改不会丢失，失败范围保留供重试。旧课程别名按原课程替换。
- 复习材料按课程缓存，材料或课程状态变化后重建对应索引。跨日重新计算日期相关状态；手动刷新可强制重新读取。
- 首页后台刷新保留现有内容，当天快照只在内容变化时写入。比较时忽略采集时间，保留最初计划额度，失败不会标记为已保存。
- Monaco 按所选语言加载语法，JavaScript / TypeScript 才加载 TypeScript 服务及其 Worker。增加 `programming-ready` 本地耗时指标，记录编辑器初始化。编辑器核心仍约 2.74 MB；此轮没有声称缩减其核心体积。

`npm run benchmark:check` 检查固定合成场景的 CPU 上限、笔记转换次数、快照写入次数和课程读取次数，输出 `.cache/performance.json`。50 次无变化读取应只触发 1 次完整课程读取和 1 次完整材料读取；修改一个课程后，两类增量读取各为 1 次。CPU 门槛见 `scripts/performance-budgets.mjs`，预留共享 CI 机器的波动空间。

构建后运行 `npm run bundle:check`，检查编辑器静态依赖总量不超过 4.2 MB、TypeScript 服务保持按需加载、重编辑器不进入启动依赖，以及正式前端不包含桌面测试桥接。当前编辑器静态依赖约 3.31 MB，结果写入 `.cache/bundle-report.json`。

`npm run test:desktop` 在独立 Tauri 应用中采集启动、首页、切课、视频、笔记和编程编辑器的实际 WebView 耗时，并执行上限检查。它测量合成课程在本机的行为，不能代表所有真实课程或操作系统。
